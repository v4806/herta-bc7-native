日期：2026-10-25。已接入安装中的 TheHerta4：`common/geometry_hash.py`、`common/submesh_model.py`、`common/native/herta_geometry_windows_x64.dll`。另为 Element 解析增加分项计时，没有改变其数据转换算法。

## 为什么采用 C + 并行

原代码把每条权重展开成顶点号、组号、权重三个 Python 值，哈希阶段再逐项类型判断、`struct.pack`、`md5.update`。虽然 MD5 本身已经是原生代码，但每个小值都通过 Python 调用一次，线程之间还争用 GIL。

新路径在主线程把 Blender 数据提取成连续数组；自制 C DLL 一次性按原顺序打包整批权重，hashlib 对大缓冲区做 MD5。ctypes 与大缓冲区 hashlib 调用释放 GIL，对象之间可以并行。

这次优化改变的是数据组织与调用粒度，**没有更换哈希算法或改变哈希字节流**。位置、组名称、权重、UV、计数字段的顺序、整数大小、float32 与 UTF-8 语义保持原实现。

## 完成内容

- 原生权重打包 C 内核，Windows x64、无 CRT/额外 DLL 依赖、不要求 AVX2，无共享状态；输入长度和影响数不一致时先拒绝再写出。
- 位置/UV 的零初始化改为原生数组重复，避免为零缓冲区先构造大型 Python 列表。
- 权重用连续列数组，减少保留在混合列表里的 Python 对象；native 输出直接交给 hashlib，避免额外 bytes 副本。
- 同一次预计算中的相同源对象只提取、计算一次，多个 draw 仍按原顺序拿到哈希与对象引用。复用按 Object 身份，不能只按共享 Mesh 判断，因为不同对象的顶点组名称可以不同。
- 默认最多 8 个对象任务并行，不再对一大堆逐项 Python pack 任务盲目开线程；显式 workers 仍可提高。该复用不跨导出持久化，防止工程修改后沿用旧几何数据。
- 缺少 DLL、ABI 不支持或 `HERTA_GEOMETRY_NATIVE=0` 时，走字节相同的批量 struct 回退。
- `[GeometryHashProfile]` 记录提取、打包/哈希、总时间、唯一/复用对象数、权重条数、线程数和 native 状态。
- `[ElementParseProfile]` 分别记录对象查找、形态键准备、求值网格、切线、属性解析、形态键还原和上下文构建，给下一轮判断哪些纯数组计算值得移入 C 提供证据。

## 本机对照：合成数据，不是实际 Blender RNA

8 个对象，各 12 万顶点；总 **96 万顶点、256 万条权重、2 层 UV**。使用 RNA 风格 Python 夹具，三个重复交错运行；所有哈希与原算法一致。提取与计算的中位数分别取自各轮，表中总时间中位数不是前两列中位数强行相加。

| 方案 | 提取中位数 | 打包/哈希中位数 | 总时间中位数 |
|---|---:|---:|---:|
| 原逐项方案 | 0.735 s | 3.181 s | **3.897 s** |
| 批量 struct 回退 | 0.628 s | 1.041 s | **1.669 s** |
| C 批量打包，串行对象 | 0.638 s | 0.377 s | **1.018 s** |
| C 打包 + 8 对象任务并行 | 0.624 s | 0.079 s | **0.704 s** |

这组对照的整段约 **5.53 倍**，耗时减少约 **81.9%**。不能把原工程的 8.42 s 直接除以这个倍数；真实 Blender RNA 属性访问和工程的数据分布没有包含在合成夹具里。

另测 1/4/8/16/32 的任务池上限，仅打包/哈希中位数约 0.376/0.099/0.077/0.073/0.074 s。**输入仅 8 个对象，16/32 是配置上限，并未产生 16/32 个同时执行的对象任务**。当前默认 8，避免把这组近似结果误解为更高线程必定更快。

持久机器可读数据：[最终对照 JSON](geometry-hash-benchmark-2026-10-25-v2.json)。前一份无 v2 的 JSON 为早期原型记录，最终比较以 v2 为准。

## 哪些还能放进 C，哪些不能只靠加线程

| 环节 | 合适的路径 |
|---|---|
| 权重排序、截断、归一化、索引映射 | 提取后可按数组批量 C/SIMD/并行；需要保持组名到槽位、异常值、排序与舍入语义 |
| UV/颜色/位置数组转换与 Buffer 打包 | 可批量原生计算并减少中间拷贝；很多 NumPy 操作已经是 C，先测 Python 调用/复制占比 |
| 索引去重 | 可以研究 C 哈希去重替换排序；当前 NumPy unique 已是原生实现，必须保持首项、逆映射、顶点 ID 和接缝特殊键 |
| Blender 网格求值、切线、RNA 数据读取 | 已有 Blender 原生实现；API 访问留主线程，优先减少重复求值和重复读取，不能任意多线程调用 bpy |
| 文件写入/INI | 受 I/O 和数据量影响，原缓冲写入约 0.09 s，当前优先级较低 |

下一重点候选为 Element 解析（原约 6.9 s）。先用新增分项日志确认是求值/切线还是权重与属性数组处理占主导，再决定后续 C 内核，而不是把 Blender API 本身搬进后台线程。
